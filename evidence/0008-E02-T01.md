# 0008-E02-T01 — A registry and a federated publisher, authored

**This is authored and unapplied.** Nothing in this packet has been applied. It creates
cloud identity and trust policy, which is the Founder's to apply, not mine.

## What applying this grants, in plain language

It creates a container registry in the landing zone's project, and one new identity that
GitHub Actions running in `work-tracker` can assume **without any key or secret** — but only
from one exact branch of one exact repository, identified by numbers that cannot be
recycled.

That identity can **push container images to one registry repository, and read what pushing
requires**. It cannot delete an image it has pushed, cannot create or reconfigure a
registry, cannot read or write the OpenTofu state bucket, cannot change any IAM policy
including its own, and cannot deploy anything. If `work-tracker`'s CI were fully
compromised tomorrow, the worst available action is publishing a bad image to one
repository — not erasing history, not escalating, not reaching the landing zone.

**It does not touch the landing zone's own federation.** `main.tf` is byte-for-byte
unchanged; the diff is empty and shown below.

## Decisions

**A separate pool, not a wider prefix — and this is the one worth reading.** The packet
asked whether a prefix is the right shape for a second tenant. It is not, and the reason is
sharper than "two conditions are safer than one". A federated principal is named
`principal://…/workloadIdentityPools/<pool>/subject/<subject>`. That name is **pool-scoped
and does not mention the provider.** Two providers inside one pool therefore mint principals
into one namespace, and the landing zone's isolation would rest on *every* provider in that
pool having a tight `attribute_condition` — forever, including providers nobody has added
yet. `work-tracker` gets its own pool, so its provider cannot name a principal in the
landing zone's pool at all. The isolation is structural rather than maintained.

Loosening the existing condition to match both repositories would also have made revoking
one tenant an edit to a string the other depends on. The packet called that the wrong
change; I agree, and did not make it.

**The publisher's role is custom, and bound on the repository rather than the project.**
`roles/artifactregistry.writer` would have worked and is one line, but it grants delete on
every repository in the project. The custom role below is push plus the reads push
performs, and the binding is a
`google_artifact_registry_repository_iam_member`, so a second registry repository added
later is not reachable by this identity without a second, visible binding.

**Retention reports; it does not delete.** `cleanup_policy_dry_run = true`. Both policies
are authored and inert: Artifact Registry logs what it *would* remove and removes nothing.
Deleting a published image is irreversible, so switching it on is a deliberate second
decision with its own plan — one line, `cleanup_policy_dry_run = false`.

**The project number comes from `var.gcp_project_number`, not from
`data.google_project.current`.** `main.tf` already asserts the two agree, in its
`project_number_matches` check. Reading the data source instead would have made every
resource in this packet unplannable without live access to the project — and the Founder
approves this from a plan. This is why the seven resources below render completely and the
two pre-existing ones that do read the data source do not.

**One exact ref, defaulting to `refs/heads/main`.** Same posture as the landing zone's own
binding. If `work-tracker` publishes from tags instead, `work_tracker_ref` is the line to
change and it needs a new apply — it is deliberately not a wildcard, and the variable
rejects one.

```
artifactregistry.files.list                         artifactregistry.tags.get
artifactregistry.packages.get                       artifactregistry.tags.list
artifactregistry.packages.list                      artifactregistry.tags.update
artifactregistry.repositories.downloadArtifacts     artifactregistry.versions.get

```

Plus exactly one binding elsewhere: `roles/iam.workloadIdentityUser` on **its own service
account**, held by the federated principal for one exact repository and ref. That is what
makes it assumable from CI at all.

**What is deliberately absent**, and each absence is a thing it therefore cannot do:

- no `*.delete` on tags, versions, packages or files — **it cannot remove an image**, so it
  cannot erase what it published
- no `artifactregistry.repositories.create/update/delete` — it cannot make a new repository
  or change this one's retention
- no `*.setIamPolicy` anywhere — it cannot grant itself or anyone else anything further
- no `storage.*` — no access to the state bucket, which is where the landing zone's
  OpenTofu state lives
- no `run.*`, `compute.*`, `container.*` — it cannot deploy
- the role is bound **on the repository**, so it reaches no other repository in the project

## What this costs

**Idle: zero.** An empty Artifact Registry repository costs nothing. The workload identity
pool, provider, service account, custom role and IAM bindings are all free — GCP does not
bill for identity objects.

**Not idle:** Artifact Registry bills storage per GB-month, list price **$0.10 per GB per
month** beyond a 0.5 GB free allowance, plus network egress at standard rates when images
are pulled from outside the region. A handful of small service images is cents per month; it
becomes real money only if image versions accumulate without bound — which is what the
retention policies address, and why leaving them in dry-run is a decision with a cost
attached rather than a free one. **Those are list prices at the time of writing and worth
confirming against current GCP pricing before approving.**

## What I could not verify

- **Nothing was applied, and nothing was planned against real infrastructure.** No GCP
  resource was created, modified or read in the landing-zone project. The plan above is
  against synthetic identifiers with no state.
- **The combined plan does not complete** — three pre-existing resources could not be
  planned, itemised in section 1. A complete single plan needs landing-zone project access.
- **The permission set is reasoned from Artifact Registry's documented Docker push path, not
  observed.** I could not push an image and watch which permissions were consulted, because
  that needs the registry to exist. If the first real push fails on a missing permission, the
  most likely candidate is a `packages`/`versions` read I have scoped too tightly — the fix
  is additive and visible in one `permissions` list.
- **`work-tracker`'s actual publishing ref is assumed to be `refs/heads/main`.** Nobody told
  me; it is a variable with that default, and if their workflow publishes from tags this
  needs one line changed and a new apply.
- **Whether `work-tracker` also needs to *pull* the image** to deploy it later. This packet
  grants push and the reads push requires. Deployment is explicitly a later packet and a
  different authority.
