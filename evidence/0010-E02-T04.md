# 0010-E02-T04 — platform-gcp reports a stale pin

This repository now reports, in its own CI, when the cost guard pin it runs is behind the
current release — on every pull request, beside the guard step itself, and on a daily
schedule that fails when the pin is stale. The guard's verdict path is untouched.

**The pin was already current, so it was not changed.** `config/cost-guard-action.txt`
reads `martcoca/cost-guard@v1.0.2`; `releases/latest` on `martcoca/cost-guard` is `v1.0.2`,
and both resolve to commit `b2721b4`. The packet's "bump it in a separate commit if it is
already stale" branch did not apply.

## What was built

| Where | Trigger | `fail-on-stale` | Why |
|---|---|---|---|
| `guarded-plan.yml`, beside the guard | push to `main`, dispatch | `false` | `if: always()`, so a **denied** plan still reports the pin's status — a denial is exactly when it matters whether the denylist in force is the current one |
| `cost-guard.yml`, its own job | pull request, push, dispatch | `false` | in front of whoever is already looking at a change, without blocking work unrelated to the guard |
| `cost-guard-freshness.yml` | schedule `17 6 * * *`, dispatch | **`true`** | the run where staleness is not ignorable |

All three consume `martcoca/cost-guard/freshness@v1.0.2` — a sub-action of the same
repository, so it ships and versions with the guard.

## Decisions the packet left to me

**`fail-on-stale` is `true` only on the schedule, as the packet proposed.** A stale pin is
not a reason to fail a plan that is otherwise fine, and it is not a reason to block a pull
request that has nothing to do with the guard. It is a reason for something to be red until
someone acts, which is what the scheduled run is for. The packet invited a different choice;
I did not need one.

**The schedule is daily at 06:17 UTC.** Daily because the thing being detected — a new
release this repository has not picked up — changes on the order of days, and T05 established
that propagation is three manual pull requests, so a faster clock would only repeat the same
message. 06:17 rather than 06:00 because scheduled workflows queue behind everyone else's on
the hour, and GitHub drops scheduled runs under load; a detector that is skipped is worth
nothing. **When the pin is stale, that run fails** — the workflow goes red and stays red on
every subsequent firing until the pin is bumped.

**The pin reaches the action from the pin file, not from a literal.** A step reads
`config/cost-guard-action.txt` into an output and the action takes that string. Writing
`pin: martcoca/cost-guard@v1.0.2` into `with:` would have created a fourth place the version
lives, free to drift from the file the contract check validates. The contract check now
forbids the literal form (seeded case 7).

**The contract check requires at least three uses of the freshness action, not exactly
three.** The three are the plan workflow, the pull-request job and the schedule; a fourth
consumer of the signal is not a defect, and pinning the count exactly would fail a future
addition for no safety gain.

## The finding: the action's documented pin-file form is broken, and it fails *confidently*

`freshness/action.yml` documents the `pin` input as:

> Point it at the same string the guard's `uses:` carries, **or at the pin file that string
> is checked against.**

`scripts/freshness.sh` never reads a file. Passing the documented path produces this:

```
$ INPUT_PIN=config/cost-guard-action.txt  (the documented second form)
cost-guard freshness: behind — pinned to config/cost-guard-action.txt ({"messa); the current release is v1.0.2 (b2721b4)
status=behind
pinned-commit={"message":"No commit found for SHA: config/cost-guard-action.txt","documentation_url":"...","status":"422"}
```

It reports **`behind`** — not `unknown`. That is the interesting part, and it is not
specific to the file form. The cause is general:

```bash
resolve() { gh api "repos/${repo}/commits/${1}" --jq '.sha' 2>/dev/null; }
```

`resolve` never checks `gh`'s exit status. When a ref cannot be resolved, `gh api` prints a
JSON **error body** to stdout, `--jq` fails, and that body is captured as if it were a
commit SHA. It is non-empty, so the `[[ -z "$pinned_commit" ]]` → `unknown` branch is dead
for this whole class of failure, and the comparison falls through to `behind`. Confirmed
against the released `v1.0.2` script (`sha256 675d0ad10a0b0c5f…`):

| Broken this way | Reports | Right? |
|---|---|---|
| the pinned ref cannot be resolved (typo, deleted tag, the documented file form) | `behind` | **no** |
| the repository cannot be resolved | `unknown` | yes |
| invalid token | `unknown` | yes |
| unreachable API host | `unknown` | yes |
| `gh` absent from `PATH` | `unknown` | yes |

The action's stated contract — "`current`, `behind`, or `unknown`. Never `current` by
default" — holds: it never falsely reports *current*. But it can falsely report *behind*,
and under the `fail-on-stale: true` scheduled run this packet mandates, that is a red job
insisting you bump a pin that is already correct. A signal that cries stale when it means
"I could not ask" trains people to ignore it, which is the epic's own failure mode arriving
by a different road.

**I did not work around it**, per the packet's instruction. This repository passes the
supported form — the pin string — so it is not exposed today. Two things would fix it
upstream, both in `cost-guard` and neither mine to make: have `resolve` check `gh`'s exit
status (`gh api … || return 1`), and either implement the file form or delete it from the
action's description. The second is the cheaper half and removes a documented path that
silently misreports.

## 5. When the scheduled run fires, and what it does

`17 6 * * *` — daily at 06:17 UTC. It checks out, reads the pin file, and asks the freshness
action whether that ref is the current release, with `fail-on-stale: true`.

- **Pin current** → step exits 0, workflow green, a `notice` annotation.
- **Pin behind** → step exits 1, **workflow red**, a `warning` annotation naming both
  versions, and a job summary saying which denials are not in force. It stays red every day
  until the pin is bumped.
- **Lookup failed** → `unknown`, exit 0, workflow green, `warning` annotation reading *"This
  is not a claim that the pin is current. It is a claim that nobody asked."*

The last one is the deliberate gap: a green scheduled run means *either* current *or*
unasked, and only the annotation distinguishes them. Failing on `unknown` would be worse —
it would give this repository's CI a network dependency its plans do not have — but it means
a sustained outage of the lookup is invisible in the workflow's red/green state alone. It is
visible in the annotation on every run.

## What I could not verify

- **The scheduled run has never fired.** Cron begins after this merges to `main`. Everything
  above about the schedule is the workflow definition plus the action's behaviour observed
  under `fail-on-stale: true` locally and on the scratch branch — not an observed 06:17 run.
- **The freshness step inside `guarded-plan.yml` has not executed in CI.** That workflow
  still fails at `google-github-actions/auth@v3` before reaching any of its steps, because
  this repository's GCP federation secrets have never been configured (recorded in
  `evidence/0010-E01-T04.md`). The step is asserted by the contract check and the identical
  action invocation is proven on the scratch branch, but the `if: always()`-after-a-denial
  path in *that* workflow remains unexercised, and will stay so until the secrets exist.
- **No `behind` verdict has been produced by a real new release.** `v1.0.1` was used as a
  stand-in for a release this repository has not picked up.
- **No cloud call, no credential read, nothing applied.** The scratch branch push and the
  pull request are the only writes.

## For whoever adopts freshness in platform-aws and platform-azure

- **Pass the pin as a string; do not pass the pin file path.** The action's own description
  offers the file form and the implementation does not support it — and it fails to
  `behind`, not to `unknown`, so it looks like a real staleness report. Read the file in a
  prior step and pass its contents, as `guarded-plan.yml` does here.
- **The freshness `uses:` will not trip your existing pin scanner** if that scanner is
  anchored like this repository's: `owner/cost-guard@ref` and `owner/cost-guard/freshness@ref`
  are different strings. Add a second scanner rather than loosening the first, and assert
  both sit at the same release — otherwise the thing asking "are you current?" can itself be
  a version behind.
- **`platform-azure` has the extra case.** Its `cost-guard.yml` checks the release out at
  `ref:` for the denylist-agreement job — an `actions/checkout` input, not a `uses:` — so it
  has a third place the version lives. `cost-guard`'s own
  `docs/dependabot-for-consumers.yml` already records this.
- **Put `fail-on-stale: true` only where a red workflow is the intended output.** On a plan
  gate it converts "your denylist is one release old" into "your infrastructure plan failed",
  which are not the same claim.
- **When you seed a failure to prove your contract check works, seed the code, not the
  comment.** See case 4 above.
