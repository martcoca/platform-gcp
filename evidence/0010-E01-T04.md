## Decisions the packet left to me

**Pinned to `@v1.0.0`, not `@v1`.** Both were permitted. The moving tag would let what is
denied change here with no commit in this repository, which is the thing the Boundary's
"do not change what is denied" protects. A denylist update should be a deliberate one-line
bump of `config/cost-guard-action.txt`.

**`scripts/check-ci-contract.sh` was wired into the `Guard` workflow.** No workflow ran it.
It was referenced only by `README.md`, so the "contract check" this packet requires to fail
an unguarded pipeline could not fail anything at all — it was a script nothing invoked.
`guard.yml` now runs it as the `CI contract` step, and the check asserts its own invocation
(seeded case 7 below), so unwiring it again fails CI. Adding the step is inside the intent
of "any contract check in this repository is updated in the same commit and still fails an
unguarded pipeline": a check nobody runs cannot satisfy that sentence.

**The check now uses `grep`, not `rg`.** Its `reject` helper was `if rg -q …; then`. Where
ripgrep is absent the shell returns 127, the branch is not taken, and every *forbidden*
pattern is reported as clean — the check fails open in exactly the direction that matters,
on any runner without ripgrep. Every assertion is `grep`-based now.

**`tofu init` keeps `>/dev/null 2>&1`; only the plan step's discarded streams changed.**
The packet's stderr complaint is about the two `2>/dev/null` on the plan-into-guard line.
The guard's own stderr is now replayed by the action into the step log and the job summary,
which is where the reason for an undecidable verdict was being lost. The plan's stderr goes
to `$RUNNER_TEMP/tofu-plan.err` — kept, not dropped, but deliberately not echoed to the
log, because this repository is public and that stream can carry the project and bucket
identifiers. Touching the init redirect would have been drift.

**`.gitignore` gained `*.plan.json`,** because `README.md` now tells a local operator to
render the plan to a file instead of piping it, and that file must not be committable.

## 1, 2 & 3. Denied fails, undecidable fails, clean passes

Run locally against a checkout of the release at `v1.0.0`, driving the action's real
entrypoint under the environment contract the runner supplies (`GITHUB_ACTION_PATH`,
`INPUT_PLAN`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`) — the same six inputs the deleted
`scripts/test-cost-guard.sh` covered, now going through the action instead of `bash
scripts/cost-guard.sh`:

```
clean-plan.json                exit=0  verdict=allow exit-code=0
denied-plan.json               exit=1  verdict=deny exit-code=1
    Denied resource: google_compute_instance.example (Always-on virtual machine): $8–70+/mo
denied-plan.jsonl              exit=1  verdict=deny exit-code=1
    Denied resource: google_compute_instance.example (Always-on virtual machine): $8–70+/mo
errored-plan.jsonl             exit=2  verdict=undecidable exit-code=2
    cost-guard: the plan reported errors; refusing to report it as clean.
    planning failed
unrecognizable.json            exit=2  verdict=undecidable exit-code=2
    cost-guard: input is not recognizable OpenTofu plan output; refusing to pass it.
empty.json                     exit=2  verdict=undecidable exit-code=2
    cost-guard: empty input; refusing to report a plan as clean.
```

Undecidable is not softer than denied: both are non-zero and both fail the step. The same
six are asserted in CI by the `action-contract` job in `.github/workflows/cost-guard.yml`,
which resolves `uses: martcoca/cost-guard@v1.0.0` on a real runner and compares
`outcome/verdict/exit-code` for each — the half a local shell run cannot cover, since
binding `uses:`, the inputs and the step outputs is the runner's job.

Also verified: the guard fails **closed** when `jq` is missing rather than finding no
denied resources. Run with a PATH that has `bash` but no `jq`, a denied fixture still exits
2 (`cost-guard requires jq to read OpenTofu plan JSON.`) rather than 0.

**What I did not do, deliberately:** the five failing steps in `action-contract` carry
`continue-on-error` so the job can assert `outcome == failure`. A job that genuinely goes
red cannot live here — auto-merge requires every check green, so a permanently-red
demonstration would block every pull request forever. The real gate is `guarded-plan.yml`,
where the guard step has no excuse and the contract check forbids one anywhere in the file.

## 4. The contract check fails on an unguarded pipeline

Eight ways to lose the gate, each seeded into the working tree and then restored:

```
1. the guard step is deleted
   Missing required contract line /uses: martcoca/cost-guard@v1\.0\.0/ in .github/workflows/guarded-plan.yml.
   It must be a real YAML line, not a mention of one in a comment.
   exit=1
2. the guard step is excused so a denial cannot fail the job
   Forbidden contract continue-on-error found in .github/workflows/guarded-plan.yml.
   exit=1
3. the action is unpinned to a branch (@main)
   Workflow uses martcoca/cost-guard@main but the pin in config/cost-guard-action.txt is martcoca/cost-guard@v1.0.0.
   exit=1
4. the plan is piped into a re-vendored local guard
   Missing required contract >"$RUNNER_TEMP/tofu-plan.json" 2>"$RUNNER_TEMP/tofu-plan.err" in .github/workflows/guarded-plan.yml.
   exit=1
5. a local copy of the guard is committed again
   scripts/cost-guard.sh is back. The guard travels with the action; a local copy is the
   duplication that extracting it removed.
   exit=1
6. the guarded plan gains a pull_request trigger
   Forbidden contract pull_request: found in .github/workflows/guarded-plan.yml.
   exit=1
7. the contract check is unwired from CI
   Missing required contract line /run: scripts/check-ci-contract\.sh/ in .github/workflows/guard.yml.
   It must be a real YAML line, not a mention of one in a comment.
   exit=1
8. the pin file is deleted
   Missing config/cost-guard-action.txt: the cost-guard release pin has no single source.
   exit=1

restored
   CI contract passed
   exit=0
```

The check also asserts what a string match alone cannot: that the guard step follows the
plan step by line number, that no `tofu apply|destroy|import|taint|state rm|mv|push`
appears in the guarded-plan workflow, that no workflow applies infrastructure, that every
`uses:` of the action in *any* workflow equals the single recorded pin, and that both
deleted files are absent **and untracked** — a file deleted on disk but still tracked comes
back on the next checkout.

No workflow gained a `pull_request` trigger. `cost-guard.yml` and `guard.yml` already had
one and keep it; `guarded-plan.yml`, `identity-check.yml` and `auto-merge.yml` do not, and
case 6 keeps it that way for the one that plans against real state. Every workflow that
triggers on push still accepts `workflow_dispatch` — `post-merge-workflows.sh check`
passes.

## The trap the packet named, and the one it did not

The three the packet named all bit as described: `check-ci-contract.sh` required
`scripts/cost-guard.sh /dev/stdin` and `scripts/test-cost-guard.sh`, both of which fail the
instant the action is used; the action takes a file path, not stdin; and the natural way to
read `outputs.verdict` off a failed step is `continue-on-error`, which removes the gate.
The reporting-step shape from `platform-azure` was copied rather than re-derived.

**The one that did not come from the packet: a fixed-string `require` is satisfied by a
comment.** The obvious contract check — `grep -F 'uses: martcoca/cost-guard@v1.0.0'` and
friends — passes a `guarded-plan.yml` whose guard step has been *deleted* and replaced by a
comment saying it used to be there. That is not hypothetical; it is what the first version
of this check did. Both halves, run against the same compromised file:

```
naive fixed-string check on the compromised file:
   CI contract passed
   exit=0   <-- the guard step is gone and this says the file is fine
scripts/check-ci-contract.sh on the same file:
   Missing required contract line /uses: martcoca/cost-guard@v1\.0\.0/ in .github/workflows/guarded-plan.yml.
   It must be a real YAML line, not a mention of one in a comment.
   exit=1
```

The structural assertions — the guard `uses:`, its `id:`, its `plan:` input, every fixture
input, and the contract check's own `run:` line — are anchored with
`^[[:space:]]*<regex>[[:space:]]*$`. A comment begins with `#` after its indent and cannot
match. The `uses:` scanner that enforces the pin is anchored the same way, so a commented-out
`uses: …@main` no longer trips it either. The `require`/`reject` pair remains fixed-string
for the assertions that really are about text appearing anywhere in a file.

## Findings about T01's interface

**The release ships two copies of the denylist.** `config/cost-guard-denylist.json` — the
one `scripts/cost-guard.sh` actually reads, at `${script_dir}/../config/` — and a
byte-identical `cost-guard-denylist.json` at the repository root. Both are `5991b73f…`
today. The repository that exists to end duplicate denylists carries a duplicate denylist,
and an editor has an even chance of updating the copy nothing reads. Worth T05's attention;
it is not worth reaching into `cost-guard` from this packet.

**The denial detail is not an output** — the same finding `platform-aws` recorded. The
action exposes `verdict` and `exit-code` only; the resource that was denied appears in the
step log and job summary but cannot be read back out of the step. It costs this repository
nothing, because `guarded-plan.yml` reports only into the job summary, which is where the
action already writes it. It cost `platform-aws` its pull-request comment body. Corroborated
here rather than re-discovered.

**The action was not awkward here in any way it was not in Azure.** In particular the
absolute-path trap `platform-aws` hit does not arise: this repository's OpenTofu root is the
repository root, so the plan step has no `working-directory` for the `uses:` step to fail to
inherit. `${{ runner.temp }}/tofu-plan.json` is absolute regardless, which is why the same
shape is correct in all three.

## Notes for whoever does the remaining consumer and T05

- **Anchor structural contract assertions to whole YAML lines.** The compromised-file case
  above is the cheapest way to end up with a check that passes an unguarded workflow, and it
  looks correct in review. `grep -Eq '^[[:space:]]*uses: owner/repo@v1\.0\.0[[:space:]]*$'`,
  not `grep -Fq 'uses: owner/repo@v1.0.0'`.
- **Check whether the contract check is actually invoked before trusting it.** Here it was
  not, in a repository that had had one for months. `grep -rn check-ci-contract .github/`
  takes five seconds and is the difference between a gate and a comment.
- **`if rg …` fails open.** Any `reject`-style assertion built on a tool that may be absent
  reports a compromised file as clean. `platform-gcp`'s check was built that way; it is not
  now.
- **A blanket "no `continue-on-error` in the guarded-plan workflow" is expressible here**
  because that workflow reports only into the job summary. `platform-aws` could not do that
  — it has a pull-request comment step that legitimately carries one — and its evidence file
  documents the line-number scoping that works and the text-subtraction that silently does
  not. Check which case you are in before copying either.
- **Write the contract check's comments without the literal strings it forbids.** A
  `reject` on `/dev/stdin` matches the comment explaining why `/dev/stdin` is forbidden.
  This check names those three spellings in a `for` loop as data, so the prose above it can
  explain the rule without satisfying it.
- **The pin file plus "every `uses:` equals it" is worth copying**, and so is asserting that
  the deleted files are untracked as well as absent.
